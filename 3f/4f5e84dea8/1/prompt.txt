P1 release blockers

1. Subject mismatch: A location/device/facility questionnaire can mount on a patient route and may be submitted as a patient response. Enforce `questionnaire.subject_type` in both frontend routing and backend submission.
2. Encounter/patient mismatch: Validate that the patient in the URL matches the encounter’s actual patient before rendering or submitting.
3. Structured-only edits are not dirty: Changes such as Time of Death can be closed without a warning or recoverable draft because structured values are excluded from dirty/autosave tracking.
4. Fill remains editable during submission: Editing while batch composition or submission is pending can produce UI/server state divergence. Freeze the session or version the submitted snapshot.
5. Studio loses edits during Save: Edits made after clicking Save are erased when the PUT response unconditionally resets editor state.
6. No Studio optimistic concurrency: Full-body PUTs have no expected `internal_revision`/ETag. Two authors silently overwrite one another. Backend should return `409` for stale revisions.
7. Fill/drafts are not revision-pinned: Local drafts compare semantic `version`, not `internal_revision`; live submissions carry no expected revision. Old answers can be accepted and stamped against a newly edited questionnaire.
8. New server drafts can 500: Draft creation resolves questionnaires by unscoped slug. Revision clones and cross-facility forms can share a slug, causing `MultipleObjectsReturned`.
9. Resumed responses are unlinked: Questionnaire submission omits `form_submission` and separately marks the draft submitted. This bypasses the backend linkage/duplicate guard and allows duplicate submissions from concurrent tabs.
10. Backend batch limit is unmodeled: Frontend creates an unlimited batch, while backend allows at most 20 requests. Twenty files plus one response, or 21 forms, deterministically fails with only a generic error.
11. Valueset-backed quantity crashes: V2 stores the selected valueset entry as `unit`, while backend validates `value.coding`. `coding=None` causes a backend 500 and full-batch rollback.
12. `exists:false` differs across layers: Frontend hides a dependent when the controlling answer is absent; backend correctly enables it for `exists:false`. Invisible required questions consequently fail at submission.
13. Required structured questions fail open: Render errors, missing context, and subject mismatches waive required validation and drop the data, while the rest of the form can submit successfully.
14. Untouched clinical records are re-upserted: Allergy, symptom, and medication-statement widgets submit all prefetched rows rather than only dirty rows. An unrelated form submission can overwrite another clinician’s concurrent edit.
15. File uploads are not truly atomic: The DB transaction rolls back on later batch failure, but S3/MinIO writes do not. This leaves orphaned clinical files and retries leak additional objects.
16. Optional appointment can use an undefined slot: Partial optional appointment data can generate `/slots/undefined/`, rolling back the full form.
17. Plaintext clinical data in localStorage: Full answers and notes persist in localStorage. TTL cleanup is lazy, auth-expiry does not consistently clear it, and same-origin plugin code can access it. Requires explicit privacy/security approval or protected server-side storage.
18. Failed login destroys recovery drafts: Drafts are cleared before authentication succeeds, so a mistyped password can delete the same user’s recoverable work.
19. Agent date/integer coercion is unsafe: Date-only input can shift by timezone or normalize invalid dates; integer questions accept decimals.
20. No durable agent audit: Agent-written clinical values are only logged with `console.debug`; persisted records do not retain agent provenance. Treat durable audit or explicit clinician acceptance as a release requirement.

P2 architecture and reliability issues

1. Questionnaire submit TypeScript types are stale and disagree with backend (`responses/value` versus `results/values/form_submission`). Raw batch URLs and `any` bodies bypass type checking.
2. Questionnaire search is subject-scoped but not facility-scoped. Users can complete a form from another facility before receiving a Save-time rejection.
3. Query data is copied into local fill-session state and can become stale when the cached questionnaire changes.
4. Changing question type can retain incompatible fields and values from the previous type.
5. Repeated valueset selections can overwrite the wrong repeated entry.
6. Missing form stores are silently skipped, allowing the rest of a multi-form session to submit without an entire form.
7. Plugin error boundaries do not reset when a plugin/type changes or recovers.
8. Plugin namespace ownership uses the remote manifest’s self-declared name rather than the trusted configured slug.
9. Action registry IDs are global and last-write-wins; it cannot safely represent multiple concurrently mounted scoped sessions.
10. Full-session JSON serialization runs synchronously on every answer edit. Studio also walks the full question tree per edit, and fill measures every question during scrolling. Large forms need performance testing and incremental state tracking.
11. The 885-line fill page mixes fetching, routing, restore, stores, autosave, actions, submission, and navigation. Introduce an explicit lifecycle state machine:
`loading → restoring → editing → composing → submitting → saved/exiting`.
12. Test helper only fetches the first 100 questionnaires, causing fixture failures once the backend contains more records. Paginate or filter directly by slug.
